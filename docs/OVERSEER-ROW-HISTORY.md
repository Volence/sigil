## LS-IS-A-BROKEN-EXISTENCE-PROBE

`state: open` · `size: XS` · `blockedBy: None`

BLAST RADIUS MEASURED: interactive-shell only - a #!/usr/bin/env bash script does NOT inherit it (tested), and scripts/ + golden/*.sh carry no bare-ls probe. Exposure is AGENT-ISSUED commands, i.e. every Bash tool call and every ad-hoc probe in every dispatch brief. ## AEON-DIR-FOLDS-TWO-QUESTIONS-BENIGNLY-FOR-NOW

`state: open` · `size: S` · `blockedBy: None`

CHECKED against aurora's two-questions-one-variable case (empyrean fb2133c) and reporting what is true rather than a match. AEON_DIR does fold both questions: provenance_chain::aeon_dir_matches_the_provenance_tip compares the tree's git HEAD against the provenance tip (question 1, 'which source revision'), while every byte comparison reads built ROMs from the SAME directory (question 2, 'which built tree do I run against'), and NOTHING ties the artifacts to the revision. But the fold is BENIGN here, for two reasons worth stating so a future reader does not re-derive them: aeon's build.sh builds IN-TREE (s4.bin et al sit in the checkout root), so the two questions have the same answer by construction; and divergence produces a LOUD RED rather than a silent pass, because the goldens are revision-specific - stale ROMs under a correct HEAD mismatch the goldens either way round. Contrast the sigil side, which is already split correctly: SIGIL_BUILD/SIGIL_EMIT name ARTIFACTS with their own names, not a <TOOL>_DIR. THE CONDITION THAT MAKES THIS REAL: if aeon ever gains an out-of-tree or configurable build output directory, the two questions separate, AEON_DIR silently answers only the first, and the byte comparisons start reading whatever is in the checkout root. Re-check at that point, not before.
