## 3 · The work-RAM delta, fully attributed

This section concerns the DEBUG shape only — the plain shape's work RAM is
byte-identical (§2a). The 64 KB work-RAM hash is identical at the boot anchor
but differs at M1/M2/M3
(OLD `FABE02A5`/`C40F7C45`/`003E6468` versus NEW `1011CB7A`/`9BCE337F`/`A7B5D7BA`).
Two hypotheses were tested and the first was **refuted by measurement**.

**Refuted — moved ROM pointers.** A symbol-table diff (committed old size tables
versus a fresh derivation) shows exactly nine boundary symbols moved, all inside
`[0x4580, 0x656E)`: `Collision_GetType`, `Collision_ProbeDown`, `Section_Init`
(−0x10) and `Camera_Init`, `Parallax_Init`, `Art_Decompress`, `BG_Init`,
`BgAnim_Init`, `Sound_PostByte` (−0x20). Every object, art, mapping and
level-data symbol is byte-stationary (`ObjCodeBase` 0x10000, `Map_TestObj`,
`Ani_Sonic`, `ObjDef_*`, `PState_*`, `DeformTable_Zero`, `HeightMaps`, `OJZ_*`),
as is every code symbol below `Tile_Cache_GetTile` 0x4580 and `EndOfRom`. No
pointer to object/art/mapping data moved, so moved pointers cannot be the cause.

**Refuted — stack return addresses.** Settled with the `BISECT1` control: the R1
generator change only, with **no `.emp` edits**, therefore **zero relocation**.
Proven zero, not assumed: `BISECT1` is byte-for-byte the golden's size in both
shapes, its **deb2 appendix is BYTE-IDENTICAL** to the golden's (so every symbol
name and address is unchanged), and it differs in exactly 27 bytes — 2 header
checksum bytes plus five 5-byte in-place stride windows containing only
`lsl.w`/`add.w` opcode words, with no address, displacement or pointer byte
touched. Run from reset under the identical anchored script:

| ROM | RAM64k | VDP combined | vram | lag |
|---|---|---|---|---|
| OLD control | `DC0E69A3` | `979FC9E9F2EF0A3E` | `49C9ACC76E3B399D` | 40 |
| BISECT1 | `5F31A007` | `979FC9E9F2EF0A3E` | `49C9ACC76E3B399D` | 40 |

`BISECT1` shows the RAM delta **with zero relocation**, which kills the
return-address explanation.

**Established mechanism — dead stack residue.** The LEADING and fully-explained
contributor is a deleted stack write, not a general argument: the old
`Section_GetSecPtrXY` `.gxy_mul` arm contained a conditional
`move.w d2,-(sp)` / `move.w (sp)+,d2` pair that this parcel DELETED. The old ROM
writes `sec_x` into that stack slot on every crossing of that arm and leaves it
as residue after the pop; the new ROM never writes it at all. That is a
guaranteed dead-stack delta with a named cause.

Alongside it, the general mechanism: the LTR chain leaves a *different, dead*
value in the scratch register than the two-power chain did (for ×80: `x` rather
than `x << 4`), and such a value reaches stack RAM on a later `movem` save and
survives below SP after the pop, where nothing reads it. This meets the porter's
static audit from the other side — all eight scratch registers dead at all nine
adopted sites, the next touch a write in every case (packet §3 table), with the
structural clincher that the pre-parcel code destroyed the SAME registers, so
liveness is unchanged and only the residual value differs.

**Two lines of evidence carry the weight**: (1) `BISECT1` — zero relocation,
same RAM delta, identical VDP, which rules out relocation as the cause; (2) the
static liveness audit, re-derived independently by the correctness lens at 8/8
sites including branch targets, the DEBUG assert block and the `.fr_no_coll`
join. The VDP identity in §2 is the observable consequence: residue that nothing
reads cannot reach the screen.

**A third line was withdrawn.** An earlier revision cited the plain shape's
byte-identical work RAM (§2a) as showing the delta appears "only where debug
instrumentation spills more registers, and nowhere else". That comparison is
between runs made under DIFFERENT scripts (plain: `press 600 → run_to →
press 180`; debug: freeze + camera sweep + 600-frame soak), so it is not a
controlled shape comparison and cannot support an "and nowhere else" clause. It
is **suggestive only** and is not relied on.

**Observed vs inferred.** The address ranges of the differing debug-shape RAM
words were not dumped, so "residue below SP" is **inferred** from the two lines
above rather than directly observed. A one-line range dump would settle it and
is the obvious first step if the question is ever reopened.

## 5 · Traps recorded (cost two full A/B passes)

1. **An A/B anchored on `pause` is invalid for a cycle-changing parcel.**
   `pause` lands at an arbitrary intra-frame instant whose phase differs between
   ROMs precisely because code timing changed, so a poke applied there lands at
   a different point within the frame and the scene diverges from the harness's
   own stimulus. Anchor on a deterministic PC (`run_to VInt_Level`) before
   poking.
2. **`reload_rom`'s diagnostic can lie.** It reported "reload was silently
   rejected" (pointer unchanged) when the load had in fact succeeded. Verify the
   cart by hashing it (`memory_hash addr 0 len <filesize>` against the expected
   CRC32), never by the reload diagnostic.
