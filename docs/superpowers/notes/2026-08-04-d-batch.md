## D1 — `[operand.const-as-address]` (S2-D12(e))

**Root cause.** A bare path in operand position is ALWAYS a symbol
(`map_plain`'s rule, `eval/asm.rs`), so `move.w RINGS_MAX, d0` emits an
absolute-address read. When `RINGS_MAX` is an `equ`, the equ becomes a real link
symbol equal to its value, so the wrong code links and runs — it loads a word
from address 999. Nothing said anything.

**Fix.** `Evaluator::check_const_as_address` (`eval/mod.rs`), called from
`map_plain`'s single-segment arm immediately before it hands back a
`CodeOperand::Sym`. Warn-tier. Exemptions in order: `@as_compat`;
`@allow("operand.const-as-address")`; a name that is not a const/equ visible in
this file (a new `local_value_names` set — the module's own declarations PLUS the
resolve pass's `use`-imported clones, which is what gives the lint its reach:
`VDP_CTRL` is an import in 14 files. Deliberately NOT the `consts`/`equs`
indexes, which also carry the whole-corpus AMBIENT slice the contract walk
injects); a `*T` pointer annotation; a value that resolves to a `Label`/
`LinkExpr`; and a value inside the measured `HW_ADDRESS_RANGE` (below).

The value probe truncates the diag list back so a bad const is diagnosed at its
own decl site, not doubly here — but truncation ALONE would be a silencer:
`resolve_const` memoizes unconditionally, including a `Poison`, so a probe that
left the entry behind would suppress the const's genuine failure at every later
use site in the same evaluator too. A probe that both CREATED the memo entry and
provoked diagnostics therefore drops the entry as well. (The
`data_item_struct_name` precedent this originally cited is NOT equivalent —
`resolve_type` does not memoize into a poisoning cache. Lens-panel catch.)

**`@as_compat` is not load-bearing on this corpus, and the packet should say so
plainly.** Spec §3 requires D1 to fire on new-style files only; `@as_compat` is
the only new-style-vs-ported marker the language has, and **zero of aeon's 122
`.emp` files carry it** — the conversion campaign modernized rather than marked.
So the exemption exempts nothing here, "new-style only" is not actually
enforceable until port markers exist, and that absence is precisely why 67 false
positives appeared and why the address-value exemption became necessary. The
mechanism is wired because it is the right mechanism, not because it does work
today.

**Judgement: 67/67 are deliberate absolute addresses. Not one is a forgotten
`#`.** The engine spells every MMIO / Z80-mailbox / RAM address as a plain
untyped `pub const` or `equ`. None carries a `*T` annotation, none is a section
label, none is an `equ`-of-label — so the spec's exemption list, written before
anyone measured, exempts NONE of them.

**What was done about it.** Not `@allow` (67 sites across 14 files is exactly
the mass-annotation the brief forbids, and would leave the lint permanently
muted where it matters most). Not silenced. Instead the address-typed predicate
gained a MEASURED fourth clause: `HW_ADDRESS_RANGE = $A00000..=$FFFFFF`.

- **Low bound `$A00000`** — where the Mega Drive map stops being cartridge space
  and starts being hardware (`$A0xxxx` Z80/YM, `$A1xxxx` I/O + bus, `$C0xxxx`
  VDP, `$FFxxxx` work RAM). A cartridge addresses its own ROM
  (`$000000`–`$3FFFFF`) by LABEL, never by a numeric constant, and the
  `$400000`–`$9FFFFF` band is extended-cart / SRAM / reserved space this engine
  never names as a literal.
- **High bound `$FFFFFF`** — the 68000 address bus is 24 bits, so nothing above
  it can be an address at all. **This bound is a lens-panel catch and it matters
  more than the low one:** the first cut was an open-ended floor, which exempted
  every 32-bit QUANTITY too. `boot_data.emp:85 const VRAM_FILL_CMD =
  vdp_comm(…)` is a VDP command long (`$4xxxxxxx`), and
  `move.l VRAM_FILL_CMD, VDP_CTRL` written without the `#` is the single most
  classic Mega Drive form of exactly the bug D1 exists to catch — the floor said
  nothing, because `$40000080 >= $A00000`. Same for `CRAM_WRITE_CMD`
  (`$C0000000`), `VSRAM_WRITE_CMD`, and any `$FFFF0000`-class mask.

Every one of the 67 corpus firings sits between `$A00000` and `$C00008`, so the
range preserves zero-corpus-firings EXACTLY while restoring detection for the
command/mask class. Re-measured after the change: **zero** firings across all
four shapes, **zero corpus edits**.

The cost is stated in the constant's own doc: a forgotten `#` on a quantity that
happens to land in `$A00000..=$FFFFFF` does not fire. That is the safe direction
for a warn-tier lint.

**Retirement condition, restated honestly** (the first version was
unreachable): this range retires when a `const` AND an `equ` can BOTH carry an
address type. The `*T` exemption reads `ConstDecl.ty`, and `ast::EquDecl` has no
`ty` field at all — its grammar is `ConstDecl` minus the annotation. 21 of the 67
firings are equs (`sound_api.emp` 17 + `vblank.emp` 4), so annotating the corpus
`*T` could never have retired it. Both halves are needed; recorded below as a
step-5 item.

**Scope held deliberately:** the first slice hooks the BARE-path form only.
`(VDP_CTRL).w` (`map_pinned_abs`) is an explicit "I mean this address" spelling
and `SOME_CONST+2` (`sym_off_operand`) is address arithmetic; neither is the
forgotten-`#`. `extern const` (L8) is also out — its address-ness is not locally
decidable, and it is the harvested-game-constant bridge.

**Tests** (`crates/sigil-frontend-emp/tests/operand_const_as_address.rs`, 11):
the classic pair in one file so the only difference is the `#` (positive asserts
exactly 1 firing, warn tier, names the const, offers `#RINGS_MAX`; negative
asserts 0 — non-vacuous because it is the same source minus one character); the
`equ` half with its kind in the message; `*T` negative; `equ`-of-label negative;
the corpus idiom (`$C00004`, `$A11100`) negative; **all four range boundaries**
(`$9FFFFF` fires, `$A00000` and `$FFFFFF` do not, `$1000000` fires) so neither
end can quietly move; **the real 32-bit shape** — `move.l VRAM_FILL_CMD,
VDP_CTRL` plus a `$C0000000` command and a `$FFFF0000` mask fire three times
while `VDP_CTRL` in the same instruction stays silent; **the probe-swallow
regression**, asserting the SPECIFIC `unknown name` message rather than "some
error exists" (measured non-vacuous: reverting the un-memoize makes it fail,
leaving only the generic "instruction dropped" floor, which names neither the
const nor the missing symbol); `@allow` in string form suppresses and the
unquoted form does not; `@as_compat` inert; a bare LABEL operand stays silent.

## D2 — `[table.name-collision]` (S2-D12(d))

**Root cause.** `enum`, `offsets`, `dispatch` and `table` all answer
`Name.Member`, and `eval_path` tries them in exactly that order. Two of them
under one name is invisible to the reader: the earlier kind wins every lookup
and the later one is unreachable. The observed symptom is a diagnostic that
names the WRONG table — `dispatch T`'s member `X` reports as
``offsets `T` has no member `X` ``. `index_items` is a map insert, so the same
kind twice is the identical hazard (last wins). The pair additionally collides
in the linker's whole-program duplicate-label pass: a late, whole-program error
for what is a one-module declaration mistake.

**Fix.** `validate_table_names` in `lower/mod.rs`, joining the existing
once-per-compile validator chain (`validate_offsets`/`validate_dispatch`/…) so it
reports once per compile, not once per per-item evaluator, at the LATER
declaration, naming both kinds and which one wins. Recurses into `section {}`
(the namespace is flat, §7.1).

**The named winner is the LADDER rank, not the declaration order** (lens-panel
catch). The first cut keyed on insertion, so `dispatch T` written before
`offsets T` reported "would silently resolve against the dispatch table" when
the actual winner is offsets — the message was wrong under half of all
declaration orders, and every test declared in ladder order so the reversal was
untested. `ordinal_ladder_rank` now mirrors `eval_path`'s arm order
(enum 0 → offsets 1 → dispatch 2 → table 3) and is documented as edit-in-lockstep
with it; a same-kind repeat has one rank, and there the message says
"last-declared" (a map insert).

**Tier is split, also a lens-panel catch.** Error tier for any pair that already
fails the link's duplicate-label check (`offsets`/`dispatch`/`table` in any
combination) — there error tier only moves an existing failure earlier and names
it properly. But **`enum` emits no base label**, so an `enum`+`offsets` module
links and runs today; making it a hard error would refuse a legal program, and
inside a warn-tier lint batch at that. Any pair INVOLVING an enum is therefore
warn-tier. The corpus fires zero either way.

**Scope note:** the plan says "offsets + dispatch"; the check covers all four
ordinal-table kinds because it is one predicate over one shared lookup ladder,
and narrowing it would leave `enum`-vs-`offsets` silently broken for no reason.
The tier split above is what keeps that widening from costing anything.

**Tests** (`tests/table_name_collision.rs`, 8): the headline pair (asserting the
named winner, not just the two kinds); **the reversed declaration order**,
asserting `offsets` still wins; **the old symptom asserted alongside the new
error** (the `offsets T has no member X` misreport still appears — proof the bug
is real and not hypothetical); the same kind twice with its own phrasing; an
`enum` pair in BOTH orders asserting warn tier and enum-wins; `table` never
winning the ladder; a section-nested declaration; and distinct names silent
(non-vacuity: four tables in one module, zero firings).

## D3 — the shadow pair (S2-D13(i) + (n))

**`[name.shadows-mnemonic]` root cause.** D-PP.1 resolves a leading bareword
against the CPU's mnemonic table FIRST and mnemonics win unconditionally
(tenet 3, `try_bare_statement_call`). So `comptime fn moveq` is callable only in
the paren form — the bare `moveq …` spelling silently assembles the instruction.

**Fix.** `validate_shadowed_mnemonics` in `lower/mod.rs`, warn-tier at the
declaration, using the SAME `is_recognized_mnemonic` predicate the bare-call path
uses (no second table to drift). Checked against BOTH CPUs plus the CPU-neutral
`jbra`/`jbsr`/`dc`, because a `comptime fn` is CPU-agnostic and the shadow bites
in whichever section matches.

**`[name.shadows-import]` root cause.** The resolve pass injects each imported
`pub data` of struct type as a type-only stub; a local `data` of that name wins
for both the base symbol and the field offsets. That resolution is correct and
ratified (ISSUE-1, `data_item_struct_name`'s doc, which explicitly ledgers "a
shadow-warning lint is ledger material"). What was missing is that the win was
SILENT.

**Fix.** `validate_shadowed_imports` in `lower/mod.rs`: intersect the
`type_only` data names with the module's own. Warn-tier at the local
declaration. **Resolution is unchanged** — this only says what already happens.

**Corpus:** zero firings for either lint, across all four shapes.

**Tests** (`tests/name_shadow_lints.rs`, 6): a 68k mnemonic fires and names the
CPU; a Z80-ONLY mnemonic (`djnz`) fires and names the Z80 (proves the both-CPU
sweep); `jbra`/`jbsr`/`dc` all three fire; ordinary names silent INCLUDING
`moveq_helper`/`lea_table` (proves the match is on the whole name, not a
substring). For (n): an end-to-end two-module build through the real
manifest→resolve→lower path (not a hand-stamped `type_only`), asserting exactly
one warning, warn tier, zero errors alongside it; plus the same consumer under a
different local name asserting zero.

## D4 — the brace-lexer extraction (S2-D13(r))

**Root cause.** `interpolate` (eager) and `interpolate_parts` (deferred) each
carried their own `{{`/`}}`/`{…}` scanner, character for character identical,
differing only in what they did with a placeholder. Two copies of a lexer is two
places for escape handling to drift.

**Fix.** `scan_message` + `MsgSeg`/`MsgScan` at the foot of `eval/guards.rs`.
Both interpolators now drive segments and keep only their own per-placeholder
policy. Diagnostic ORDER is preserved: the scanner stops at an unterminated `{`
and hands its tail back, so the caller emits the same single error after the same
preceding placeholder errors, and appends the same literal text.

**Behaviour: none changed.** The gate is the existing parity suite —
`eval_guards` (21), `lower_guards` (12), `here_provisional` (8), all green — plus
4 new unit tests on the scanner itself (escapes+placeholder ordering; the
unterminated tail with its preceding literal preserved; plain/empty templates;
`{}` as a placeholder rather than a literal).

## Step-3 (what the port/parcel taught the LANGUAGE) vs step-5 (what it taught the ENGINE)

### Step 3 — language/tooling findings

1. **A spec's exemption list written before measurement is a guess.** D1's
   `*T` / section-label / `equ`-of-label enumeration matched 0 of 67 real
   address constants. The lint was only shippable after a corpus sweep told it
   what an address actually looks like in this codebase. Any future
   "warn unless X" lint should be swept BEFORE its exemption list is fixed in
   the spec.
2. **Warning-tier diagnostics are invisible in the production build path.**
   `sigil_harness::native::build_emp` filters `bdiags` for `Level::Error` and
   drops the rest on the floor; `run_build_native` never renders them. A
   warn-tier lint can therefore fire on the whole corpus and leave no trace in
   `build.sh` output. The D1 sweep needed a temporary hook to see anything. **A
   `--warnings` (or `SIGIL_SHOW_WARNINGS`) surface on the native build path is a
   real gap** — 156 pre-existing warnings are currently firing on the corpus and
   nobody sees them (51 `[proc.sr-undeclared]`, 10 `[proc.clobber-undeclared]`,
   6 `[proc.undeclared-fallthrough]`, 3 `[proc.out-unwritten]`). Gap-ledger
   material; arguably the highest-value item this parcel surfaced after D1
   itself.
3. **`local_value_names` vs the ambient env.** `Evaluator::consts`/`equs` are
   polluted by the corpus-contract walk's ambient slice, so any per-file lint
   that asks "is this name in scope HERE?" must build its own set — and must be
   clear that after the resolve pass "in scope" means own + `use`-imported, not
   own only (`collect_pub_comptime` clones every imported `pub const` into the
   consumer's `file.items`). Worth knowing before the next name-based lint.
4. **A comptime probe that swallows its diagnostics must also un-poison the
   memo.** `resolve_const` memoizes unconditionally, so
   snapshot-truncate-restore is NOT sufficient to make a probe side-effect-free:
   the entry survives and silences the real use site. Any future lint that
   speculatively resolves a const needs the same pairing. The existing
   `data_item_struct_name` idiom is not a precedent here — `resolve_type` has no
   poisoning cache behind it.
5. **A lint whose exemption is a numeric threshold needs BOTH bounds argued.**
   D1's first cut was an open-ended floor, which silently exempted the entire
   32-bit quantity space — including the `vdp_comm()` command longs that are the
   most classic instance of the bug. On a 24-bit-bus target "is an address" is a
   RANGE predicate, and the ceiling was the load-bearing half.
6. **`@as_compat` cannot express "new-style only" on a fully-converted corpus.**
   Spec §3 gates D1 on new-style files; the only marker is `@as_compat` and no
   aeon file carries it. Any future ported-vs-authored distinction needs a real
   port marker, or the spec should stop promising the distinction.
7. **D2's "promote the incidental test" instruction had no referent.** The plan
   inherited "incidental" from a 2026-07-08 sanctioned NOTE, not a test. Plan
   rows that say "promote the existing test" should name it.
8. **A diagnostic that names a WINNER must derive it from the resolution rule,
   not from source order.** D2's first cut keyed on insertion and was wrong under
   half of all declaration orders, undetected because every test happened to
   declare in ladder order. Tests for order-sensitive messages must include the
   reversal.

### Step 5 — engine findings

1. **The engine has no way to say "this constant is an address" — and the
   LANGUAGE cannot express it for half of them.** 29 distinct MMIO /
   Z80-mailbox / RAM constants are plain untyped `pub const`s or `equ`s; `*T`
   exists and is used by nobody. Typing them (`pub const VDP_CTRL: *u16 =
   $C00004`, or a `HwPort` newtype) would let D1 drop the `HW_ADDRESS_RANGE`
   heuristic, make `move.w VDP_CTRL, d0` vs `move.w #VDP_CTRL, d0`
   type-distinguishable, and feed the T2 newtype tier. **But it is not
   sufficient on its own:** `ast::EquDecl` carries no `ty` field, and 21 of the
   67 firings are equs (`sound_api.emp` 17, `vblank.emp` 4). Retiring the range
   needs BOTH a corpus annotation pass AND an `equ NAME: T = …` grammar
   increment. The corpus half is ~30 edits across 4 files and belongs to the R2
   per-file retrospect or an S2-D8 tier ruling; the grammar half is a language
   increment nobody has asked for yet. Recorded as a pair so neither is
   attempted alone.
2. **156 unaddressed corpus warnings** (see step-3 item 2). The 51
   `[proc.sr-undeclared]` firings in particular are a contract-completeness
   signal that Track B′ should look at, and they have been silently accumulating
   because nothing prints them.
3. Neither bucket: the workspace clippy backlog (above) and the fact that the
   `demo` shape's synthetic entry emits a "whole-module `use` imports no names"
   warning for `engine.debug.error_handler` on every build.
