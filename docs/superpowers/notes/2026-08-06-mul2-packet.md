## 6 · THE FINDING THAT OUTRANKS THE PARCEL

**`EntityWindow_MigrateMasks` strides `Entity_Scan_State` by 22 where the record
is 26 bytes. It has been wrong since 2026-07-31. It is the SECOND instance of a
class this ledger already barred.**

`struct EntityScanState (size: $1A)` = 26, `ENTITY_SCAN_STATE_LEN = $1A`
(`engine/ram.emp:37`), and every other indexing site in the module uses
`sizeof(EntityScanState)` — `:603`, `:789`, `:819`, `:926`, `:1350`,
`:1452-1458`, `:1548-1554`, `:1678-1681`, `:1746` (the last two re-resolved by
reading the file in the fixup round — they had been cited 6 lines short). The `.new_loop` head of
`EntityWindow_MigrateMasks` instead spells the stride as a hand shift chain
computing **×22**, then reads
`Entity_Scan_State + d0 + offsetof(ess_section_id)`.

| entry | reads offset | should read | lands in |
|---|---|---|---|
| 0 | 18 | 18 | correct |
| 1 | 40 | 44 | `ess_rom_type_tbl_ptr` byte 2 |
| 2 | 62 | 70 | `ess_rom_obj_ptr` byte 2 |
| 3 | 84 | 96 | `ess_rom_ring_ptr` byte 2 |

All stay inside the 104-byte array, so there is no out-of-bounds access and no
crash — ROM-pointer bytes are simply read as section ids.

**The consequence is sharper than "masks are not migrated", and it runs in both
directions.** `EntityWindow_InitSection` (`:630`) zeroes an entry's loaded mask
ONLY when that entry's section CHANGED (`cmp.b EntityScanState.ess_section_id(a1),
d1 / beq .same_section`, `:634-646`), and `EntityWindow_Slide` runs
`BuildEntries` — hence `InitSection` — BEFORE `MigrateMasks`. So:

- **(a)** an entry that CHANGED section has a zeroed mask and then fails the
  identity match on a garbage id, so its surviving section's already-spawned
  entities are re-treated as unloaded: **duplicate spawns**, not merely
  un-migrated masks;
- **(b)** an entry that KEPT its section has a correct, non-zeroed mask, and
  `MigrateMasks` still walks it — a garbage byte that chance-matches an old
  snapshot id reaches `.match`, which copies a **foreign** 32-byte mask over a
  correct one, corrupting an entry that needed no migration at all.

The follow-up parcel's A/B must be designed to exhibit BOTH. Same family as the
symptom the first instance produced; the duplicate-spawn direction is new.

**Provenance, git-verified rather than inferred.** Commit `4ad9f9b` (2026-07-31,
"entity_window #1 — per-section trigger cache") grew the struct `$16` → `$1A`
for two new trigger-cache fields and updated every `sizeof`/`offsetof` site and
both `ensure`s. `git show 4ad9f9b~1` and `git show 4ad9f9b` show the eight-
instruction chain byte-for-byte unchanged across that commit — it was CORRECT at
×22 the moment before and wrong the moment after.

**This is a recurrence.** The ledger row at ~1349 ("Hand-computed struct strides
are a BYTE-GATE BLIND SPOT", 2026-07-22) records the same proc, the same array
and the same chain breaking in the OPPOSITE direction: the `$1A` → `$16` cut left
it at ×26. That row's BAR — *any struct field-count/size change greps the module
for hand-computed strides, not only symbolic `sizeof`/`offsetof`* — was in the
ledger and was not applied nine days later.

**Why nothing caught it.** The byte gate is structurally blind (the wrong stride
is what golden and fresh build agree on). Boot is blind (a wrong mask is not a
crash). And the stale-comment tell that caught it the first time is present
again, twice: `:48` says the records are "$16 bytes each" and the chain's own
comment says "entry stride $16" — both false since `4ad9f9b`.

**Not fixed here, deliberately.** The fix is a BEHAVIOUR change, and it must not
ride inside a byte-proof optimization parcel whose A/B is an identity check — a
correct fix will make the two ROMs behave DIFFERENTLY on a window slide, which is
the point, and an identity A/B cannot express that. It needs its own parcel with
an A/B designed to EXHIBIT the difference: slide the window across a section
boundary with entities already collected in a surviving section, and watch the
masks migrate. Ledgered OPEN with the fix spelling
(`#sizeof(EntityScanState)`, with the caveat that `sizeof(...)` specifically —
as opposed to a named `const`, which §5 measured — should be confirmed by that
parcel).

**The two stale comments ARE fixed, and a KNOWN-BUG marker now sits at the
chain** (`9f5e459`). Until the fixup round the defect was recorded only in the
sigil ledger; the aeon repo carried nothing but the two false comments, so a
reader there had every reason to re-derive ×22 as intentional. The marker names
the ledger row, states both consequences, and says explicitly that the stride is
not to be fixed as a drive-by.

**Step-5 (engine findings, not taken).**

0. **§6 — the MigrateMasks stride bug.** A live defect, a recurrence, and a
   refused adoption site. It outranks everything else here.
1. **A construct adoption is a stronger fix for the hand-stride class than the
   BAR that class already has, and this parcel is the evidence for both halves.**
   The 2026-07-22 row asked authors to REMEMBER to grep for shift decompositions
   after a struct-size change; nine days later they did not. A
   `mul_const.w dst, #<derived>, scratch` spelling needs nobody to remember
   anything — the multiplier derives, so a size change either updates it or fails
   the build. §5's rider is that argument applied to the two ×80 sites. The
   general shape: **every hand-decomposed constant multiply whose constant is a
   struct size, entry stride or array pitch is a latent instance of this class**,
   and the multiply construct's real value is not the 8 cycles it saved at
   `Collision_GetType` — it is that a construct call can carry a derived constant
   where a shift chain can only carry a literal. Ledgered OPEN as a census ask;
   corpus-wide exposure is **unmeasured**, which is stated rather than guessed.
2. **The "this guard is now vacuous" argument was WRONG, and the way it was wrong
   is the most transferable thing in the parcel.** The reasoning was locally
   valid — once a multiply takes `#TILE_CACHE_STRIDE`, that site cannot disagree
   with the constant, so its own `ensure` guards nothing. What it missed is that
   an `ensure` is not scoped to the line above it: it fails the BUILD, so it
   protects every site in the corpus that shares its assumption. Deleting it
   traded a global tripwire for a local proof. **A guard is vacuous only when
   every site relying on its assumption has been made structurally safe** — here
   that was 2 of 8, counted this session. The 5a deletion one level up looks like
   the same move and is not: there the "absence" being pinned had no other
   consumers, which is exactly what was verified before deleting it.
3. `Section_FlatIDXY`'s `.fxy_mul` and the two `tile_cache.emp` ×80 sites remain
   deferred by overseer ruling, gated on the three-address form. **The ruling is
   correct and this parcel found no reason to reopen it** — all three are blocked
   by the same in-place-construct/contract-widening seam, and §5's derived-
   immediate rider does not help them (it changes what the immediate may be, not
   how many operands there are).
