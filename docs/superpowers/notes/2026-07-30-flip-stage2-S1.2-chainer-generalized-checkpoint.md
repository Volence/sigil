## THE FINDING — declared SIZES are load-bearing (correct ORDER is not sufficient)

The ratification framed the soundness condition around ORDER ("the golden byte-gate
would catch a mis-order loudly — iteration-cost, not corruption risk"), implicitly
assuming that, given the correct order, chaining reproduces the golden. **It does not.**
Empirically (the throwaway probes behind this commit):

- **Pure content-size chaining diverges from asl.** Packing each section by its relaxed
  `final_size` produces **15955 header-neutral diffs**, first at `0x391` (a −2 in
  `boot`). Root cause pinpointed: sigil's link relaxer grows short→long; when sections
  pack tighter than asl's layout, a branch sitting exactly at the `.s`/`.w` boundary
  relaxes SHORTER, so the chained ROM settles at a *different, tighter* relaxation
  fixpoint than asl. First drift is `vblank.emp` → `hblank` slips **−2**, and it
  cascades (every downstream section −2, then more). Both directions fail:
  - advance by `max(reserved_span, final_sz)` (the linker default) → OVER-reserve →
    `+0x2ac` by `HeightMaps`, overlapping the phased sound bank (link error).
  - advance by `final_sz` (reserved_span=0) → UNDER-reserve → the −2 cascade above.
- **The fix: reserve each section's DECLARED SIZE = its exact asl per-region span.**
  Then the computed-base chain reproduces asl's ADDRESSES, which anchors relaxation to
  asl's WIDTHS → 0 diffs both shapes. This is what `build_native_rom_chained` does.

So the map manifest (SPEC2:199) must declare per-region **sizes**, not just order, and
those sizes are sourced per target from its asl listing. Bases stay computed — the
soundness condition (no baked-address dependency for the base) is preserved; the SIZE
is a declared datum, exactly the manifest's job.

## The consequence for demo/Config (why this is a checkpoint, not a silent detail)

The sonic4 gate captures its declared sizes from a **pinned pass-1 resolve** (pin at
the baked lmas, which for canonical sonic4 ARE asl-correct → the resolve reproduces asl
→ each section's post-relax `image_len` is its exact asl span). **This trick is
sonic4-only.** Demo's AS residual carries the WRONG sonic4 resume orgs, so a demo
pinned pass-1 lands everything at sonic4 addresses and captures sonic4 spans — useless
for demo. Demo/Config must get their per-region sizes from **their own asl listing**:

- **emp region sizes** ← boundary-label deltas in `demo.lst` / the Config listings
  (the "demo pin table" of `2026-07-30-flip-stage1-demo-lockstep-scoping.md`, now shown
  to be REQUIRED, not merely a cross-check — the size, not just the base, is needed).
- **AS island sizes** ← `image_len` directly (AS residual is pure Data — its span is
  address-free, no listing needed).

This is the same information as the "demo pin derivation" sub-project already scoped,
but the finding sharpens WHY: without the exact per-region asl sizes, chaining a
sound-off demo layout will land at a different relaxation fixpoint and miss the golden.

Reconnaissance done this session (grounding the recommendation):
- `./build.sh demo` (positional) rebuilds fresh to the golden **18c64002/90776**;
  `demo.lst` carries 21344 labels incl. every boundary label the region table needs
  (EntryPoint/BootData/GameLoop/AnimateSprite/ObjCodeBase/Section_Init/BG_Init/
  BusError/EndOfRom). The demo pin/size derivation is feasible with the `repin`
  listing parser pointed at `demo.lst` + the engine-only region subset.
